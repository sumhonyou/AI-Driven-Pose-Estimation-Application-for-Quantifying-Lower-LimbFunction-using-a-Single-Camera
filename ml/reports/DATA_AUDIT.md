## 3. The view question — verified, not assumed

`Segmentation.txt`'s own mapping table (see the schema doc's "known documentation
inconsistency" section) implies: when `cam17_orientation == "front"`, the subject faces
camera17 dead-on, and camera18 — mounted orthogonally — sees them from the side. This
was **visually verified** against real frames, not taken on faith:

![View verification: front vs half-profile, Camera17 vs Camera18](figures/view_verification.png)

- **`cam17_orientation == "front"` (`PM_008` rep 1, frames 100–220):** Camera17 shows
  the subject squarely facing the camera (frontal). Camera18 shows a clean, true
  sagittal/profile view — full body visible in silhouette, hip/knee/ankle stacked in
  the image plane exactly as a side-on functional assessment needs.
- **`cam17_orientation == "half-profile"` (`PM_008` rep 18, frames 3940–4050):** Both
  Camera17 and Camera18 show the subject at a diagonal angle — **neither camera is a
  true side view** for these reps.
- **`cam17_orientation == "profile"` never occurs for Ex6** (0 of 195 reps) — it only
  appears for Ex3 (107 rows), an exercise this project doesn't use. So the mapping
  table's third row (profile → front) has no Ex6 rows to apply to.

**Conclusion: for Ex6, the usable side-view source is `cam17_orientation == "front"`
rows, read from the Camera18 video file.** `half-profile` rows have no usable
true-sagittal camera and are excluded from the "usable side-view" count below.

## The gate

**Do not proceed to Stage 5.2 until HY chooses.** Per `task.md`'s Stage 5.0, three
options are presented with trade-offs — none chosen here:

**(a) Accept the smaller N (98 reps, 72 Good / 26 Poor) and report it as a limitation.**

- Pro: simplest, cleanest "side-view only" story for the write-up (X3-consistent, no
  new feature).
- Con: 26 Poor reps is a small minority class for LOSO with 9 subjects; 3 of 9 LOSO
  folds (subjects 2, 4, 9) would have **zero Poor examples in the held-out fold**,
  making per-fold Poor-class metrics undefined for those folds (Stage 5.5's own
  documented fallback — stratified group k-fold — becomes close to mandatory, not
  optional).

**(b) Additionally admit half-profile reps as a separate, flagged cohort; test whether
including them helps or hurts LOSO.**

- Pro: recovers the missing Poor examples — half-profile Ex6 reps: **97 total, Good 62 /
  Poor 35** — without abandoning the strict side-view definition for the "clean"
  cohort. Combined (side-view + half-profile) would give Good 134 / Poor 61, i.e. the
  full unfiltered Ex6 set.
- Con: half-profile is a materially different camera geometry (confirmed visually above
  — not a small perturbation), so features computed on it (especially anything
  angle-based) are not directly comparable to the side-view cohort's; needs its own
  validity check (a variant of Stage 5.4) before being trusted, not just a "does it
  help the metric" test.

**(c) Relax to both views and add `view` as an explicit feature.**

- Pro: keeps the full 195-rep Ex6 set, no wasted data, and makes any geometry effect
  explicit and modelable rather than hidden.
- Con: directly cuts against this project's Locked Assumption #3 ("Side (sagittal) view
  only... frontal knee valgus is dropped from the taxonomy") — a `view` feature
  reintroduces exactly the geometry-dependence that assumption was written to avoid,
  and the production/live system only ever captures one camera, so a model trained
  partly on `half-profile` features would need `view` supplied at inference time too,
  which the live capture pipeline does not currently produce.

No option is chosen here. Recording numbers only, per the gate's instruction not to
decide unilaterally.
